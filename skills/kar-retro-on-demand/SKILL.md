# 目的
在人类要求或触发条件命中时，把一次交付转成可复用的系统改进，而不是流水账或追责。

# 触发

- 人类说“复盘一下”；
- 出现 S0/S1 或逃逸缺陷；
- 返工 ≥2 轮或超期 >50%；
- Program 收尾时人类要求。

复盘不阻塞合并；可在 H3 后或合并后独立进行。不触发时在 issue 记录“未复盘 + 理由”。

# 一、输入

issue 时间线、运行日志、文档版本、commit/PR、CI、测试证据、决策记录、人类评论、原型评审/一致性记录、manifest 与 metrics。

# 二、分析

- 时间线：受理 → H1 → H2 → A3 → 开发 → A4/A5 → H3 → 合并；标等待/返工/阻塞。
- 质量：覆盖、缺陷、返工、逃逸、门禁结果。
- 效率：lead time、active time、人类等待、交接、合并队列；用 `scripts/metrics.py report` 的 5+1 指标与 2 周基线，不凭感觉。
- 协作：派发是否清晰、HANDOFF 是否完整、人类卡片是否可读、哪些决策太晚。
- 原型：是否减少 H1 后变更与返工；像素级一致性是否带来额外成本。
- 系统根因：指令、Skill、平台、流程、工具、环境、人类响应。
- 改进：3–5 条，含 owner、截止、验证方式；区分本次补丁与机制改进。

# 三、报告

复盘分析文档.html 至少：

1. 文档控制、需求摘要、最终结果/发布状态
2. 目标与实际对照
3. 端到端时间线与关键节点
4. 质量度量与缺陷分析
5. 效率度量与等待/返工
6. 各 Agent 与人类协同表现（基于行为/产物，不做人格评判）
7. 做对了什么（可复制机制）
8. 做错了什么/差点出错（含根因）
9. 关键决策复盘
10. 改进措施（owner/due/验证/预期）
11. 需要更新的 Skill/指令/项目规则（只建议，不直接改）
12. 证据索引与数据口径

数字注明来源与计算方法；没有数据写“未采集”。

# 四、质量自检

- 至少一个反事实分析。
- 至少一个系统性改进，不能只写“下次注意”。
- 区分偶发与系统、Agent 执行与指令设计。
- 建议可验证，例如“把 A3 的 RTM 检查加入 Lead 门禁，下一需求起 100% 检查”。

# 五、交接与禁止

HANDOFF：stage=retrospective、artifacts、key_findings、actions、proposed_changes、evidence。

不追责个人；不修改本次结论；不直接改 Skill/配置；不把复盘变成流水账；不编数字。
