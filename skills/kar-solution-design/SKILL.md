# 目的
把已批准的需求与原型转成可实现、可测试、可运维、可回滚的设计。

# 触发
H1 已批准；工作道 Standard/Program。

# 一、设计流程

A. 建立 FR/NFR/SC 覆盖矩阵，找缺口。
B. 选择最小必要架构：组件、边界、依赖、数据流、控制流；说明为什么不选更复杂方案。
C. 定义接口/事件/数据模型/错误码/幂等/兼容性/版本策略。
D. 定义失败与安全：异常、超时、重试、降级、权限、隐私、输入校验、审计。R3 必须产出威胁模型与权限矩阵（资源 × 角色 × 动作，默认拒绝，每条拒绝有越权测试），并把扫描/回滚演练要求写进设计。
E. 定义 NFR：性能预算、容量、可用性、可观测性、可维护性；每条可度量。
F. 定义交付：配置、迁移、灰度、回滚、监控、告警、运维；无迁移/回滚不得进入 H2。
G. 定义可测试性：测试接缝、数据、环境、可控时钟、故障注入、验收测试执行方式。
H. 写 ADR：背景、选项、决定、后果、复审条件；覆盖架构风格、数据、外部依赖、安全、兼容性。
I. 产出 HTML、H2 简报、风险与未决问题。

# 二、原型覆盖矩阵

- 读 H1 原型、SC 映射、UI profile、H1 批准记录；不只看截图或摘要。
- 每个 SC 映射到设计章节与验证方式；关键交互、状态、权限、错误、空态必须有设计落点。
- 原型与设计不一致：记录偏差、原因、影响、推荐方案；重大交互/视觉取舍进 ADR，并在 H2 确认。
- 不缩小已批准原型的交互/视觉范围；不以“原型没画”为由省略需求。

# 三、方案设计文档

至少：文档控制/H1 引用、目标/约束/非目标、FR/NFR/SC 覆盖矩阵、架构总览、数据模型/迁移、接口契约、流程/状态机、权限/安全/隐私/审计、性能/容量/可用性/可观测性、兼容性/i18n/可访问性/可维护性、部署/配置/灰度/回滚/运维、测试策略/可测试性、ADR、风险/假设/依赖/未决、需求变更影响、原型覆盖/偏差、变更记录/审批栏。

# 四、质量自检

- 每个 FR/NFR 有覆盖，无孤儿设计。
- 每条 NFR 可度量；每个失败路径有处理。
- 迁移/回滚可执行；安全/权限不是一句话。
- 不超出 H1 范围；新增范围回 H1。
- 可被 TestDesigner 转成用例；不能则先补可测试性。

# 五、H2 与交接

- H2 卡前先发设计草稿，至少提前 **10 分钟**异步 review；草稿记录写 `checkpoints.h2_draft`，纠偏由 Lead 记 `steers`。
- H2 卡：方案 v + 原型覆盖矩阵 + 风险/未决 + 建议；R3 附威胁模型/权限矩阵摘要。
- 完成后 HANDOFF：stage=design、branch/head、artifacts、coverage、decisions、prototype_matrix、risks、open_questions、recommended_next。
- 建议下一步：TestDesigner 可测性预审，然后 H2；不自行批准或进入开发。
