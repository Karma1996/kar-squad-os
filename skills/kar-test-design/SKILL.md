# 目的
在开发前定义“怎样才算对”，用可执行验收测试固定它。

# 触发
H1 已批准；H2 前做可测性预审；H2 后做 A3 测试设计。

# 一、两种模式

- **TESTABILITY_REVIEW**（H2 前）：审查测试接缝、数据、环境、可观测性、故障注入、验收自动化可行性；只输出结论与缺口。
- **TEST_DESIGN**（H2 后）：用例、RTM、可执行验收测试、A3 包。

# 二、方法

- 风险驱动：用户影响 × 概率 × 可检测性 → P0–P3。
- 技术覆盖：等价类、边界、状态迁移、决策表、组合、并发、幂等、权限矩阵、失败注入、迁移、兼容性、可访问性。
- 每条 FR/AC 至少一个用例；P0/P1 至少一个可执行测试或明确手工理由。
- 用例：前置条件、数据、步骤、期望、实际（执行时填）、优先级、自动化映射。
- 非功能：阈值、数据集、测量方法、环境；不能只写“性能良好”。
- 原型：为关键 SC 交互、状态、权限、空/错/载入补测试；除非 AC 明确要求，不做像素级复刻测试。

# 三、可执行验收测试

- 只调用公开接口/UI/CLI；不依赖实现私有细节。
- 测试代码与用例同分支；可先红，但记录“预期失败”；开发后不偷偷改期望。
- 数据可重复创建/清理；不依赖生产数据；不写真实凭据。
- 命名映射 TC 编号；运行命令/环境/依赖写入文档。
- 无法测试的 AC：停止，向 Lead 提决策请求；不用模糊断言掩盖。

# 四、A3 就绪包

- 用例文档 v1.0 + RTM 完整。
- 可执行测试已提交；运行方式明确；当前状态（红/未运行）与原因记录。
- 环境、数据、依赖、mock 边界、已知缺口写清。
- 开发完成后应运行的测试命令清单。
- 结论：`READY_FOR_DEV / NOT_READY` + 阻塞项。

# 五、交接

HANDOFF：stage=test-design/testability-review、artifacts、tests、commands、traceability、risks、open_questions、recommended_next。建议下一步 A3 评审，然后 Dev；不自行实现或宣布通过。

# 六、禁止

不写业务代码；不代替 QA；不为速度减少 P0/P1 覆盖；不自行解释不清需求。
