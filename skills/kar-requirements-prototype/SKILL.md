# 目的
把人类意图转成可验证的需求基线；在大/复杂 UI 时产出高保真、像素级、契合项目风格的原型，作为 H1 与开发的基线。

# 触发
工作道 Standard/Program 的需求阶段；Quick 触发 UI 条件时升级 Standard。

# 一、问题优先

- 需求要素未齐（目标/用户/范围/FR/AC/NFR/Repo Impact/Docs Home/原型判定）：只发 QUESTION BATCH。
- **一次最多 5 问**；每问给选项、推荐、默认、影响。
- 人类不回答：`waiting_human:questions`；不自动补默认、不进入 H1。
- 人类说“先出草稿”：输出带 `DRAFT / unresolved` 的草稿，不能作为 H1 基线。
- 人类回答后：先复述“我理解的决定”，再写正式文档。

# 二、需求分析文档

至少包含：文档控制、背景/问题、目标/成功度量/非目标、用户/角色/场景、FR、NFR（可度量）、AC（Given/When/Then，映射 FR）、业务规则/权限/数据/隐私、异常/失败/恢复、范围/假设/依赖/风险、开放问题（负责人/截止/默认）、FR→AC 追溯、决策/变更记录、术语表。

自检：每个 FR 至少一个可测 AC；每个 AC 有明确通过/失败；范围外有记录；没有凭空补全。

# 三、原型触发

| 触发 | 不触发 |
| --- | --- |
| 新页面/新导航/信息架构变化 | 纯文案、颜色、间距、图标替换 |
| 多步流程/新状态机 | 复用现有组件的小改动 |
| ≥3 个新 UI 状态 | 纯后端/API、纯数据 |
| 多角色/权限影响可见性/操作 | 已有成熟模式的小 CRUD |
| 响应式/可访问性新交互模式 | 纯视觉微调且不改变行为 |
| 新组件模式/设计系统变更 | |
| 需求歧义大/返工成本高 | |

- Lead 提议，Decision Owner 在 H1 确认；可覆盖。
- 不触发：需求文档 + H1 卡写“not required + 理由”。

# 四、从代码提取 UI 风格（默认）

不要求人类手工给色板；按优先级提取：

1. 设计系统/tokens：CSS variables、SCSS variables、Tailwind config、theme 文件、`tokens.json`。
2. 组件库：Button/Input/Modal/Card 等及其样式、变体、尺寸。
3. 现有页面：布局、导航、间距、字号、圆角、阴影、图标、文案语气。
4. 品牌资源：logo、字体、图片、可访问性配置。

产出 `ui-profile`（项目事实或 `multica/project/ui-profile.json`）：

```json
{
  "source": ["src/styles/tokens.css", "tailwind.config.ts"],
  "tokens": {"color": {}, "font": {}, "space": [], "radius": [], "shadow": []},
  "breakpoints": ["375", "768", "1280"],
  "theme": ["light", "dark"],
  "a11y": "WCAG AA",
  "constraints": []
}
```

- 提取成功：原型必须使用这些 token/组件形态，不得引入第二套视觉语言。
- 提取失败：找 2–3 个现有页面；仍无法确定用中性 fallback，并在 H1 卡标“风格假设”，由 Decision Owner 确认。
- 不把真实数据、生产密钥、未授权字体/图片放进原型。

# 五、原型交付（模式 B）

- 自包含 HTML，离线可开，`file://` 可读；不加载 CDN、外部字体、外部 CSS/JS。
- 使用项目 token/组件形态；颜色、字号、间距、圆角、阴影、图标、密度一致。
- 覆盖主流程、关键分支、loading/empty/error/success、校验、权限、响应式断点、暗色（如支持）。
- 固定假数据并标注；不接真实后端；不用真实个人数据。
- 评审模式：标注可开关；`SC-001…` 映射 FR/AC。
- 关键状态可点击到达；键盘可操作；对比度/焦点满足项目可访问性。
- 原型与需求文本冲突：停止，提交决策，按人类决定同步修改。

# 六、H1 包

- 需求文档 + 原型 + SC 映射 + 评审记录 + 版本/commit SHA。
- H1 批准绑定两者 + 模式 B（像素级）。
- H1 后可见变化（页面/布局/导航/状态/交互/文案）→ 重开 H1 或变更记录；纯实现细节不变可见结果不需要。
- 不触发原型时写“not required + 理由”。
- Program：跨工作流 UI 用父级原型；各工作流独立页面放 `workstreams/{slug}/交互原型.html`；父级做索引与统一风格，H1 一次批准整套。

# 七、H1 后

- 把原型、SC 映射、UI profile 一起交给 Architect；设计必须给 `SC → 设计 → 实现 → 验证` 矩阵。
- 发现需求/原型冲突：停止，交回 Lead，不自行改基线。
- 不进入设计/开发；只做需求阶段。

# 八、完成定义

需求与原型已提交并推送；自检通过；SC/FR/AC 可追溯；UI profile 有来源；证据可复现；H1 包完整；下一步建议唯一。
