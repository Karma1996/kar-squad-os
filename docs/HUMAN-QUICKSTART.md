# 人类快速上手（1 页）

KAR Delivery Squad 的目标是让你只做人类该做的事：**决定、选择、指定人**。其余由 Agent 执行并附证据。

## 你只需要记两个命令

- `/approve`：同意当前这一步（所有门通用，不需要记 H1/H2/H3）。
- `/init`：项目初始化，一个项目一次。

其他都用大白话：要改直接说“把 X 改成 Y”；要停说“先停”；看进度问“到哪了”；指定人说“验收找 A，方案找 B”。

## 每个门你会看到什么

一张卡，固定 8 行：

```text
🟡 需要你：确认需求基线（v1.2 / a1b2c3）
谁决定：你
先看：3 分钟摘要 → <链接>；原型 → <链接>
我检查了：① 范围与验收标准一致 ② 原型版本/SHA 一致 ③ 证据可复现
理由：需求与原型覆盖全部 P0，范围未漂移
附条件：无
回复：/approve　要改：直接说“把 X 改成 Y”
不做：停在这里，不会自动通过；24h 后只提醒一次
```

- 你只需要回复 `/approve` 或一句明确的“批准 + 版本/范围”。
- 表情、沉默、“看起来还行”不算批准；Lead 会复述并绑定版本/SHA。
- 每个 Decision Owner 同时最多 2 个待决策；多出的 Lead 会排队，不会一次全发。
- 24h 没回应只提醒一次；不会自动通过，也不会有人代你批。

## 你的责任

- 在 SLA 内回应（默认 24h）；指定备份人。
- 批准前至少看 1 页摘要；附条件批准要写清条件。
- 不替 Agent 跑测试、对 diff、查配置；这些由 Agent 做并附证据。
- 不把 token、密码、生产数据发到 issue。

## 你要改小队配置时

1. 在 **KAR Squad OS** 项目开 issue，写目标、验收、影响、回滚。
2. Agent 在分支实现；CI 绿后你评审 PR。
3. 你 Approve 后合并、打 tag、构建 release。
4. Agent 部署到工作区并 `verify.py`；执行前自动备份。

## 不会操作时

直接问“现在要做什么”，Lead 会给你下一步；不要猜，也不要跳过门禁。
